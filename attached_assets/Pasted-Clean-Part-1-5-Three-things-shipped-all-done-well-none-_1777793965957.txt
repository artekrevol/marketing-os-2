Clean Part 1.5. Three things shipped, all done well, none of them invented scope-creep. Brief read on each:
Brand-voice timeout work
The tagged error classes (OpenAITimeoutError / OpenAIRetriesExhaustedError / OpenAIRetriable / OpenAINonRetriableError) are better than just throwing strings. Sprint 9's Performance Monitor will be able to graph "% of runs failing on OpenAI timeout vs. rate limit vs. 5xx" without parsing error messages. That's worth the extra five minutes it took to model.
The 408/429/5xx + abort + network retry policy is the right list. Specifically: 408 Request Timeout is rare from OpenAI but exists; including it costs nothing and catches a real edge case. Not retrying on other 4xx is correct (401 = bad key, 400 = bad request body, neither gets better with retry).
Worst-case wall clock at ~90s + backoff for a hung call is acceptable for now. Worth flagging for Wave 2: when Performance Monitor lands, watch the p95 brand-voice check duration. If it creeps past 30s regularly even on success, the timeout is too tight and you'll see false-error rates. Easy to widen later.
The deps seam (fetchImpl/timeoutMs/retryBaseMs) for testing is the right shape. Future check implementations should follow this pattern — every external call with a deps seam means the unit test doesn't need network access. Good convention to lock in.
Event splitting
qa.check_failed (subject = qa_run) vs. qa.check_errored (subject = qa_check_result) is the right semantic distinction. A failed check is something about the qa_run as a whole; an errored check is a specific result row that didn't compute. Subscribers in Sprint 7+ will benefit from this — Decision Engine cares about run-level outcomes, Performance Monitor cares about check-level outcomes.
buildCheckResultEvent extracted as a pure function for unit testing is the right move. Sprint 9's Performance Monitor will likely need to backfill these events for older qa_runs once it ships; having the function pure means a backfill script can call it without spinning up the worker.
The terminal-status fix (errorCount contributing to qa_run.status='error') catches a real bug. Without it, if all four checks errored cleanly via the new outcome='error' path, the qa_run would have stayed in a confused state. Hard-fail-wins, error-beats-pass is the right precedence.
Tests
11/11 green is good. The end-to-end shape test for brand-voice (DB + env mocked, asserts outcome/attempts/errorClass on a hung call) is the kind of test that catches regressions when someone refactors retry logic six months from now. Worth the effort.
