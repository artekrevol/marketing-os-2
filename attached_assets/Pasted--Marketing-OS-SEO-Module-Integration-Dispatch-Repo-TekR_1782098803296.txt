# Marketing OS — SEO Module Integration Dispatch

**Repo:** TekRevol Content Platform (Marketing OS) — Replit
**Source codebase:** SEO-main (uploaded separately — standalone keyword/rank tracking tool, source-of-extraction only)
**Target module:** `artifacts/seo-os` (already exists; currently houses Quality Gate + Recovery)
**Dispatch type:** Single consolidated change. Sequential, do not subdivide.

This dispatch lands keyword research, rank tracking, competitor discovery, and crawl scheduling inside Marketing OS — using the platform's existing patterns (Drizzle schema in `lib/db`, BullMQ worker tier, `withBrandScope()` tenancy, session-based auth, Wouter routing in `seo-os`). The source code in SEO-main is a reference; do not merge it as a unit. Take what's listed, leave the rest.

---

## What's already in place (grounded in the most recent architecture survey)

- Monorepo, pnpm workspaces. Node 24, TS 5.9, ESM.
- `artifacts/seo-os/` exists — React 18 + Vite + Wouter, currently routes Quality Gate (`/quality-gate`) and Recovery.
- `lib/db/src/schema/` — Drizzle schema. Tables in place: `user_profiles`, `projects`, `outlines`, `drafts`, `research_briefs`, `voice_library`, `usage_logs`, `recovery_*`, `qa_*`, sessions.
- `lib/integrations/` — DataForSEO client and Originality.AI client present. DataForSEO is dormant (taken off deployment). This dispatch reactivates and extends, not rebuilds.
- `lib/jobs/src/types.ts` — job-type registry. `lib/worker/src/jobs/index.ts` — dispatch.
- BullMQ queues: `maintenance`, `integrations`, `projects`, `content`, `scoring`, `ai`.
- Auth: `requireAuth` middleware (express-session + bcryptjs + Postgres-backed sessions), `assertBrandAccess` / `assertBrandAccessForProject` / `requireProjectAccess` for brand-scoped routes.
- Multi-tenancy: app-layer only. `BRAND_SCOPED_TABLES` allow-list + `withBrandScope()` / `ScopedDb` wrapper.
- Critical finding: `BRAND_SCOPED_TABLES` already names `keyword_lists`, `rank_snapshots`, `competitor_pages` — the schema for these doesn't exist yet. This dispatch fills that gap using those names, not SEO-main's table names.

## Goal

After this dispatch, an authenticated user with appropriate brand access can — from inside the existing SEO OS frontend at `/seo-os/`:

- Manage keywords and keyword lists, scoped to their active brand.
- Manage geographic locations for SERP tracking.
- Trigger ad-hoc crawls or schedule recurring rank checks.
- View current rankings and ranking history for any keyword × location.
- Discover and review competitors surfaced from SERP data, blacklist irrelevant ones.
- See competitor insights (overlap with TekRevol keyword set, content gaps).

All data is brand-scoped through `withBrandScope()`. All routes use the existing auth + brand-access middleware. All async work runs on the existing BullMQ tier.

## Phase 1 — Schema additions

Add nine tables to `lib/db/src/schema/seo.ts` (new file). All brand-scoped tables follow the existing Marketing OS pattern: `brand_id` column, snake_case names, foreign keys to existing tables where applicable. **No `seo_*` prefix** — these are first-class platform entities, named per the allow-list convention.

### 1.1 Tables

```typescript
// lib/db/src/schema/seo.ts

// Geographic targets for SERP queries
locations              // id, brand_id, name, country_code, region, city, dataforseo_location_code, language_code, created_at, updated_at

// Keyword collections (lists of keywords for tracking)
keyword_lists          // id, brand_id, name, parent_list_id (self-FK, nullable for hierarchy), description, created_at, updated_at

// Individual keywords being tracked
keywords               // id, brand_id, keyword_text, list_id (FK → keyword_lists, nullable), location_id (FK → locations), search_volume, cpc, competition, last_checked_at, created_at, updated_at

// Point-in-time ranking results
rank_snapshots         // id, brand_id, keyword_id (FK), location_id (FK), batch_id (FK → crawl_batches), position, url, found_at_position (boolean), serp_features (jsonb), captured_at

// Batch metadata for crawl runs
crawl_batches          // id, brand_id, status (enum: pending/running/complete/failed), keyword_count, completed_count, started_at, finished_at, error_message, created_at

// Recurring crawl schedules
crawl_schedules        // id, brand_id, list_id (FK → keyword_lists, nullable — null means all keywords), cron_expression, active, last_run_at, next_run_at, created_at, updated_at

// Competitor URLs surfaced from SERP data
competitor_pages       // id, brand_id, competitor_domain, url, keyword_id (FK), position, captured_at

// Aggregated competitor intelligence
competitor_insights    // id, brand_id, competitor_domain, shared_keyword_count, average_position, top_keywords (jsonb), last_computed_at, created_at, updated_at

// Domains excluded from competitor discovery
blacklisted_domains    // id, brand_id, domain, reason, created_at
```

Place in `lib/db/src/schema/seo.ts`. Re-export from the schema barrel. Do not co-mingle with content-engine tables (briefs, drafts, etc.) — keep separate file for legibility.

## Phase 3 — Worker jobs

Crawls, rank checks, competitor discovery, and competitor-insight computation run async on BullMQ.

### 3.1 New job types — `lib/jobs/src/types.ts`

Add four typed job definitions. Naming follows the existing registry's convention:

- `seo.crawl.run` — execute a crawl batch (one batch = N keywords × M locations)
- `seo.rank-check.scheduled` — triggered by `crawl_schedules`; enqueues a `seo.crawl.run` for the right keyword set
- `seo.competitor.discover` — for a given keyword set, pull SERP data and upsert `competitor_pages`
- `seo.competitor-insights.compute` — recompute `competitor_insights` for a brand (e.g. weekly)

All payload schemas in the registry. All include `brandId` so the worker can `withBrandScope()`.

### 3.2 Worker handlers — `lib/worker/src/jobs/seo/`

One handler per job type. Each handler:

1. Validates payload against the registered schema.
2. Wraps work in `withBrandScope(payload.brandId, async (db) => { ... })`.
3. Uses the DataForSEO client from `lib/integrations/dataforseo/`.
4. Writes results via Drizzle through the scoped DB handle.
5. Updates batch/job status fields.

### 3.3 Queue assignment

Use the existing `integrations` queue. Do not create a new queue. If queue back-pressure becomes a real problem after launch, a `rank-tracking` queue can be split out later — out of scope for this dispatch.

### 3.4 Scheduled jobs

Use BullMQ's repeatable jobs primitive. On startup, the worker reads `crawl_schedules` where `active = true` and registers a repeatable job per row. When a schedule is created/updated/deactivated via the API, the API publishes a job-registry event the worker consumes. Use the existing event/dispatch pattern from the codebase rather than introducing new infrastructure.

### 3.5 Idempotency

Per the existing convention, deterministic `jobId`s prevent double-runs. For `seo.crawl.run`, jobId = `crawl:${batchId}`. For scheduled rank checks, jobId includes the scheduled timestamp.

## Operational notes

- **DataForSEO Secrets** must be set in Replit Secrets (`DATAFORSEO_LOGIN`, `DATAFORSEO_PASSWORD`) before Phase 2 testing. Agent halts cleanly if missing.
- **Cost shape**: every DataForSEO call hits real money. The crawler in SEO-main has rate-limiting and batching; preserve both during the port. Each call logs to `usage_logs` so per-brand spend can be audited.
- **Page parity over enhancement.** The goal is functional parity with SEO-main's user experience, not improvement. Do not redesign pages, do not consolidate routes, do not refactor the crawler. Improvements come in follow-on dispatches once SEO functionality is shipped and stable.
- **No `seo_*` table prefix.** Marketing OS conventions are plain names (`keyword_lists`, `rank_snapshots`). SEO-main's names are different; the dispatch's Phase 1 mapping is authoritative.
- **No Clerk introduction.** The frontends ship dead Clerk deps; do not wire Clerk during this dispatch even if SEO-main happens to use it. (It doesn't, but flagged.)
- **No new `/data` directory.** A separate content-quality-fix dispatch (deferred) will introduce a file-based asset loader for the playbook and reviews bank. This dispatch does not touch that.
- **TanStack Query keys** are namespaced `['seo', ...]` — enforce consistently.
- **Diagnostic pages intentionally omitted.** Three "Test" / "Diagnostic" pages in SEO-main are dev utilities and stay out of the production module.
- **No data migration** from SEO-main's existing database. Users start fresh in Marketing OS.
- **Schema drift risk.** The platform currently uses `drizzle-kit push` without committed migration files. This dispatch follows that pattern but the underlying risk is real — a separate dispatch to introduce a production migration story is recommended.
- **Open questions surfaced by the architecture survey**, deferred to separate dispatches: Clerk cleanup (dead deps removal), Supabase ghost cleanup (.replit stale references), Anthropic SDK adoption, production migration story. None of these block the SEO integration.
