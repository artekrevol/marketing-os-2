# Content Plan Architecture Dispatch (Replit)

**Repo:** TekRevol Content Platform (Marketing OS) — Replit
**Objective:** Replace the current validator-patch model with a Content Plan architecture: a planner AI produces a structured plan (specific selections, budgets, styles) between intake and generation; Rabia reviews and adjusts the plan before generation runs; generation writes to the plan; validation checks plan compliance rather than accumulating rules.
**Dispatch type:** Substantial multi-phase architectural change. Comparable in scope to the SEO Integration + Shared Data Layer dispatches combined. Structured with an early pause point (after Phase 3) so Rabia can begin using admin surfaces while later phases build the operational core.

## Context

Cut A (candidate injection), Cut B (content-shaping prompt tightening), Playbook v2.5 upload, and the SEO Dashboard data migration have all shipped. Rabia tested through July 10 and left substantive review feedback on the architecture design document (July 17).

The current architecture separates candidate selection (retrieve from DB), generation (LLM produces content), and validation (check output against accumulating rules). Every bug surfaced during Rabia's testing was addressable only as another validator patch — "reject nav-type page_types," "strip repeat URLs," "require citation path depth," "add brand mention floor." Each patch treats a symptom rather than a cause.

This dispatch commits to the architectural alternative: a Content Plan sits between intake and generation. The plan makes explicit every decision the model would otherwise make on its own — how many links, which specific ones, how many brand mentions and what style, which testimonials, which specific report URLs for citations. Generation writes to specifications rather than freestyling.

**Rabia's role transforms.** Today she reviews finished articles and fixes problems. Under this architecture, she reviews the plan before generation runs and adjusts every budget, swaps specific selections, sets template defaults through a Rules Dashboard. Editorial judgment gets applied upstream, not downstream.

**Explicitly integrated feedback from Rabia (July 17 review):**
- Brand mentions capped at 4-5 per article regardless of funnel stage, with mentions classified by *style* (project spotlight, service highlight, credential reference, first-person authority, team specificity) rather than counted uniformly
- External citations: DR 80+ domains only, max 3 per article, no source older than 3 years
- Named projects tagged by industry + keyword tags for planner-driven relevance matching
- Content tone requirement: affirmative, definitive, solution-oriented (no hedging, no ambiguous neutrality)
- Rules Dashboard: central admin surface where Rabia sees and edits every default the system uses, organized by content type

**Explicitly out of scope for this dispatch:**
- Competitor data quality audit (separate small hygiene dispatch — SEO team sanitizes competitor list, sanitized set becomes ground truth for future discovery)
- AI Research module (LLM citation UI — 47K rows preserved in the platform from the migration, module builds later)
- Infographic pipeline integration
- Perplexity as research source
- Multi-language or campaign-level planning

## Phase 1 — Schema foundation

Scoped transactional DDL. No blanket `drizzle-kit push`.

### 1.1 Content plans table

```sql
BEGIN;

CREATE TABLE content_plans (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  brand_id uuid NOT NULL REFERENCES brands(id) ON DELETE restrict,
  project_id uuid NOT NULL REFERENCES projects(id) ON DELETE cascade,
  template_id uuid REFERENCES content_plan_templates(id) ON DELETE set null,
  status text NOT NULL DEFAULT 'draft',
  plan_data jsonb NOT NULL,
  provenance jsonb NOT NULL DEFAULT '{}'::jsonb,
  planner_reasoning text,
  estimated_cost_usd numeric(10,4),
  approved_at timestamptz,
  approved_by uuid REFERENCES users(id),
  superseded_by uuid REFERENCES content_plans(id),
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX content_plans_brand_project_idx ON content_plans(brand_id, project_id);
CREATE INDEX content_plans_status_idx ON content_plans(brand_id, status);
CREATE UNIQUE INDEX content_plans_active_per_project ON content_plans(project_id) 
  WHERE status = 'approved' AND superseded_by IS NULL;

COMMIT;
```

`status` values: `draft`, `under_review`, `approved`, `superseded`, `abandoned`. Only one approved plan per project at a time (partial unique index). Superseding a plan (regenerating with different parameters) creates a new row and updates the old row's `superseded_by`. Add to `BRAND_SCOPED_TABLES` allow-list.

### 1.2 Content plan templates table

```sql

CREATE TABLE content_plan_templates (
```

Templates are versioned. When Rabia edits a template through the Rules Dashboard, a new version is created; old versions retained for plan lineage. Add to `BRAND_SCOPED_TABLES`.

## Phase 4 — Planner AI stage

The core intelligence.

### 4.1 Planner service

New service: `lib/content-ai/src/planner/`

Entry point: `generatePlan(intakeParams, researchOutput, brandContext): Promise<ContentPlan>`

Inputs:
- Intake parameters (topic, keyword, location, content type, ICP, funnel stage, writer notes)
- Research output (SEO context, SERP top-10, competitor URLs, LSI terms, SERP features)
- Brand context: active template for the content type, global rules, playbook, reviews bank filtered by industry/keyword tags, link targets filtered by cluster/funnel, named projects filtered by industry/keyword tags

Output: complete Content Plan JSON conforming to schema.

### 4.2 Plan schema

The plan is structured JSON stored in `content_plans.plan_data`. Structure includes:

**meta:** schema_version, generated_at, template_id, template_version, global_rules_snapshot (frozen at plan draft time).

**article_structure:** target_word_count, section_count, sections array with per-section: order, kind, heading, target_word_count, must_contain_primary_keyword, must_contain_direct_answer, required_elements.

**brand_voice:** total_mention_target (default 5), mention_style_distribution (array of section+style pairs, with named_project_id if style is project_spotlight), voice_register, icp_calibration, affirmative_tone_required.

**testimonials:** array with review_id, placement_section, reason, source.

**internal_links:** array with link_target_id, url, anchor_text, placement_section, reason, source.

**external_citations:** target_count (default 3), max_count (default 3), min_domain_rating (default 80), max_publication_age_years (default 3), selections array with domain, specific_url, publication_year, domain_rating, claim_supported, placement_section, reason, source.

**project_matching:** industry_filters, keyword_filters, matched_projects array with project_id, match_score, match_reasons, spotlight_section.

**seo:** primary_keyword, primary_keyword_target_occurrences, primary_keyword_placement_required, secondary_keywords, lsi_terms_available, lsi_terms_target_coverage, title_tag spec, meta_description spec.

**cost:** estimated_input_tokens, estimated_output_tokens, estimated_cost_usd, max_cost_usd, model.

**provenance:** per-field map tracking source of each value ("template.cost_guide:v3", "global_rules.citation_authority:v2", "planner_ai:decision_id:xyz", "rabia_manual_override").

### 4.3 Planner AI call

Model: Claude Haiku for cost efficiency (planner call is smaller than generation).

Structured tool use pattern: the planner is prompted with all inputs and asked to emit the plan as a tool call with the plan JSON as the payload. Deterministic parsing, structural validation.

System prompt (abbreviated):

> You are the content planner for TekRevol Marketing OS. You produce Content Plans that specify exactly what an article will contain.
>
> Your inputs: intake parameters, research findings from SEO OS, the active template for this content type, brand rules, and the assets available (reviews bank filtered by relevant tags, link targets, named projects, authority citations).
>
> Your output is a complete Content Plan conforming to the schema. Every selection must reference a real entity ID from the provided assets. Every budget must respect the template and global rules unless the article specifically warrants deviation.
>
> Specific decisions you make:
> 1. Which testimonials (specific review IDs) best serve which sections, considering vertical/industry match, recency, and quote content
> 2. Which internal links (specific URLs) support which sections, considering cluster fit and no-repetition
> 3. Which external citations (specific report URLs, not domains) support which claims, considering DR threshold and publication age
> 4. Which brand mention style goes in which section, considering funnel stage and topic
> 5. Which named project(s) to spotlight based on industry+keyword tag overlap
> 6. What section structure best serves the topic given SERP competitors and content type template
>
> When you cannot find a good match for a required selection (e.g., no whitelisted testimonial fits the vertical), flag the gap in the plan for Rabia to resolve manually. Do not force a poor match.
>
> Every decision must include a `reason` field explaining why.

### 4.4 Planner cost gate

Before generating the plan, compute estimated cost. If estimated cost exceeds the template's max, flag for Rabia. If daily brand cap would be exceeded, flag. Not a hard block — surfaces as a warning in the Plan Review UI.

Commit: `Phase 4: Planner AI service + plan schema`

## Phase 6 — Generation writes to plan

Rewrite the outline, draft-section, and final-stitch prompts to accept plan parameters explicitly.

### 6.1 Outline stage

Currently the outline stage figures out its own structure. Replace with: the outline is now taken directly from `plan.article_structure.sections`. No AI call needed — the outline is a deterministic transformation of the plan into the format the draft stage expects.

Migration: keep the existing outline route as a fallback for legacy projects without plans, but new projects skip outline generation and use the plan's section list directly.

### 6.2 Draft-section stage

System prompt for each section becomes:

> You are writing Section {order} of this article: {kind}, heading "{heading}".
>
> **Word budget:** Exactly {target_word_count} words (±10% tolerance).
>
> **Must contain primary keyword:** {yes/no}. Placement: {intro/H2/closing}.
>
> **Brand mention this section:** {style} — with style-specific instructions:
> - project_spotlight: "Reference our work on {named_project.name}. The project was: {project.problem_summary} We: {project.approach_summary} Outcome: {project.outcome_summary}"
> - service_highlight: "Highlight our {service_area} practice with specific capabilities"
> - credential_reference: "Reference TekRevol's credentials — 280+ engagements, ISO 27001, specific vertical experience"
> - first_person_authority: "Use first person authoritatively — 'we've seen', 'in our experience'"
> - team_specificity: "Reference specific team characteristics — 'our Karachi delivery team', 'our AI practice'"
>
> **Internal link this section:** {specific URL} with anchor text "{anchor_text}"
>
> **External citation this section:** {specific URL} — supports claim: "{claim_supported}"
>
> **Testimonial this section:** From {reviewer_name} of {company}: "{quote}"
>
> **Required elements this section:** {list of elements the section must contain}
>
> **Tone:** Affirmative, definitive, solution-oriented. No hedging. Direct answers.
>
> Manual instructions from editor: {rabia_manual_instructions_relevant_to_this_section}

The model no longer has choices about how many links or which testimonial. It writes the section using the specifications.

### 6.3 Final-stitch stage

Now handles:
- Assembling sections into complete article
- Extracting ARTICLE_TOOL schema (which now includes plan compliance data)
- Generating meta_description within 150-155 char target
- Generating title_tag within 50-60 char target
- Generating FAQ block per plan spec (question count, answer word range)
- Generating JSON-LD structured data
- Generating author byline per plan spec

Extractor prompt receives the plan and article. Its job is to assemble the article's structural output honoring the plan's targets exactly.

Commit: `Phase 6: Generation writes to plan`

### 6.4 Plan enforcement pass (deterministic)

After generation, before validation, run a deterministic enforcement pass:

- If article emits more internal links than plan allows: strip excess by section placement match
- If article emits duplicate internal links (same URL twice): strip duplicates
- If citation URL doesn't match plan's specific URL: strip citation, log deviation
- If word count per section is off by >15%: log warning, no action
- If required element missing: log critical, regenerate that section with reinforced instructions

The enforcement pass runs before human review, so Rabia sees an article that already conforms to plan structure.

Commit: `Phase 6.4: deterministic plan enforcement pass`

## Phase 7 — Validation as plan compliance

Retire the 24-check matrix. Replace with Plan Compliance Report.

### 7.1 Plan Compliance Report

For each plan field, generate a compliance row:
- Field name
- Plan target
- Article actual
- Delta
- Disposition: PASS, WARN, FAIL

Dispositions:
- **PASS:** actual matches plan target exactly or within tolerance
- **WARN:** actual within tolerance but flagged (e.g., word count off by 12% is within 15% tolerance but worth noting)
- **FAIL:** actual outside tolerance or required element missing

FAIL dispositions block ship until Rabia manually accepts or regenerates.

### 7.2 Universal validators (kept)

Three rules stay as validators independent of the plan (they're never negotiable):

1. **Fabricated testimonial validator** — every testimonial in the article must exist in `reviews_bank_entries` (exact match on reviewer_name + company, quote_excerpt within edit distance).

2. **Confidentiality validator** — no client marked confidential in `reviews_bank_entries` appears in the article.

3. **Banned phrase validator** — banned phrase list from global_rules is checked against article text.

### 7.3 Retired validators

Remove or subsume the following (they're now handled by plan enforcement):

- Nav-page filter (subsumed by planner's link selection)
- Internal link no-repeat rule (subsumed by plan enforcement pass)
- Citation depth requirement (subsumed by planner's specific URL selection)
- Brand mention range validator (subsumed by plan's style distribution)
- H1 count validator (subsumed by plan structure)
- Keyword placement validator (subsumed by plan's placement requirements)
- Meta description length validator (subsumed by plan target)
