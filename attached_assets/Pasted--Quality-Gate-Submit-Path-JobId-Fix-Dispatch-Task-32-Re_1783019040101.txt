## Context

Task #28 fixed multi-colon jobId violators in AI research and recovery snapshot jobs. During that investigation, a related zero-colon violator was surfaced in the quality-gate submit path:

`content.qa-run-checks` jobs enqueued from `lib/services/quality-gate/src/actions.ts` use `idempotencyKey: qaRunId` where `qaRunId` is a colon-free UUID. The resolved jobId is `content.qa-run-checks:<uuid>` = 2 parts. The `buildJobId` guard requires exactly 3 parts (exactly one colon in the idempotencyKey).

This path fires on every draft submission for review. Higher blast radius than the #28 fixes because it's on a hot code path — Cut B and Blog #1 regeneration will exercise this path repeatedly.

## Scope

### 1. Two call sites in `lib/services/quality-gate/src/actions.ts`

- Line 156: `submitForReview` function — enqueue of `content.qa-run-checks`
- Line 476: `runChecks` function — enqueue of `content.qa-run-checks`

### 2. The fix

Prefix a constant segment so the resolved jobId lands at exactly 3 parts:

```typescript
// Before
idempotencyKey: qaRunId  // resolves to "content.qa-run-checks:<uuid>" = 2 parts

// After
idempotencyKey: `qa:${qaRunId}`  // resolves to "content.qa-run-checks:qa:<uuid>" = 3 parts
```

Apply identically at both call sites. Both must use the same prefix pattern.

### 3. The stored `qa_runs.id` in the database is NOT touched

Only the BullMQ jobId string changes. Database rows, foreign key relationships, and any code reading `qaRunId` from the DB stay exactly as they are. This is a jobId-hygiene fix only — no data model changes.

### 4. Extend the existing regression test

The `buildJobId` test in `lib/worker/jobs/seo/enqueue-jobid.test.ts` (or wherever the equivalent test lives per Task #28's additions) needs a new accept case:

- Accept: `qa:<uuid>` → resolves to 3 parts
- Reject: bare `<uuid>` → resolves to 2 parts (was the old shape)

### 5. Typecheck across affected packages

`pnpm run typecheck:libs` and any package that depends on the quality-gate service must pass clean.

### 6. Restart the worker and confirm clean boot

Same clean-boot verification as Task #28: worker status RUNNING, no error/throw/enqueue lines in the log, no crash loop.
